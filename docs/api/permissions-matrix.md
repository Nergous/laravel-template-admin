# Permissions matrix and error catalog

Who may call which admin route, how the checks are layered and which errors come
back. Source of truth: `routes/web.php`, the FormRequests in `app/Http/Requests`,
the policies in `app/Policies`, `App\Services\Access\RbacGuard` and the services
in `app/Services`. The full route list (`php artisan route:list`, regenerated by
`composer doc:routes`) is in [routes.snapshot.txt](routes.snapshot.txt).

## Authorization model

One mechanism (`spatie/laravel-permission`, permission names `module.action`),
with one job per layer (docblock of `App\Http\Controllers\Controller`):

1. **Route middleware** (`permission:x` in `routes/web.php`) decides whether the
   user may perform the action at all. Create/edit routes carry both the
   section's `*.view` and the action permission (`*.create`, `*.edit`), resource
   routes attach the action permission with `middlewareFor()`. A user with
   `users.view` but without `users.create` gets **403** on `POST /admin/users`
   from the middleware.
2. **Record-level rules** live in Laravel policies (`App\Policies\UserPolicy`,
   `App\Policies\RolePolicy`, auto-discovered) and are applied on the route with
   `can:` middleware (`can:update,user`, `can:delete,role`, …). A record above
   the actor answers **403**, including the GET edit pages. Where the ability
   depends on the payload, the FormRequest asks the policy instead
   (`DestroyUserRequest`: `delete`, or `forceDelete` with `force=1`).
3. **FormRequest `authorize()`** re-checks the same concrete permission (defence
   in depth, never just "signed in"). List pages take a `*FilterRequest` that
   validates the filters (a malformed value is a validation error) and
   whitelists sorting and page size (`SortsList`, `PaginatesList`).
4. **Controllers** do not repeat permission checks. Bulk actions apply the
   per-record rules in their service and report skipped records in the flash
   message instead of failing the request.
5. **Services** keep the domain invariants (anti-escalation, protected roles,
   your own account) whoever calls them, and report them as 422.

`can()` in Vue (`resources/js/lib/can.ts`, fed by `auth.can`) only hides
buttons. The server stays the source of truth.

### Superadmin and roles

- **Superadmin** is the role named in `config('rbac.superadmin_role')`
  (`admin`). `Gate::before`, registered in `App\Providers\AppServiceProvider`
  (it asks `RbacGuard::isSuperadmin()`), lets it pass every ability and policy
  check, including route `permission:` middleware, so a missing permission row
  can never lock it out. `auth.can` lists every permission for it.
- The superadmin role's permission set is **immutable**: the matrix locks its
  column, and the role form and the matrix reject any change with 422.
- **System roles** (`roles.is_system`: `admin`, `operator`) cannot be deleted or
  renamed; only a superadmin may change their permissions or assign them.
- **Role management rule** (`RolePolicy::update` / `delete`): a non-superadmin
  may edit or delete a role, toggle its matrix cells or assign it to a user only
  when it is not a system role and they hold **every** permission the role has
  (`RbacGuard::missingPermissions()`). They may grant only permissions they hold
  themselves (`RbacGuard::canGrantPermission()`, the `GrantablePermission` and
  `AssignableRole` validation rules). This stops a `roles.edit` or
  `permissions.edit` holder from stripping the role of someone above them. The
  role resources expose the result as `can_delete`.
- **User management rule** (`UserPolicy::update` / `delete` / `restore` /
  `forceDelete`): a non-superadmin may edit, block, delete, restore or delete
  permanently a user only when the target has no system role and no permission
  the actor lacks (`RbacGuard::coversUser()`). Everyone may manage their own
  account, but cannot remove the superadmin role from themselves, block or
  delete themselves (service rules, they apply to the superadmin too). Keeping a
  role the user already has is not a new grant. The user resources expose the
  result as `can_manage`.
- **Permissions** are defined in code (`RolePermissionSeeder::PERMISSIONS`,
  migrations through `App\Support\Migrations\PermissionMigration::add()` and
  `::rename()`), so they carry no "system" flag. The panel only toggles the role
  × permission matrix: there are no routes to create, rename or delete a
  permission.

Permissions: `users.{view,create,edit,delete,export}`,
`roles.{view,create,edit,delete}`, `permissions.{view,edit}`,
`media.{view,upload,edit,delete}`, `activity-log.{view,delete}`,
`settings.{view,edit}`, `backups.{view,download,create,delete}`,
`queue.{view,manage}`. The `operator` role gets the media permissions by default
(`RolePermissionSeeder::OPERATOR_PERMISSIONS`).

## Notation

- All URIs are relative to `/admin`.
- **Route** — the `permission:` / `can:` middleware (or `guest`/`throttle`).
  Every route except the login form also runs `auth`, `AuthenticateSession` and
  `EnsureAccountIsActive`.
- **Request** — the FormRequest and what it checks in addition, when it differs.

| Method | URI | Route | Request / notes |
| ------ | --- | ----- | --------------- |
| GET | `/roles`, `/roles/{role}` | `roles.view` | list: `RoleFilterRequest` |
| GET | `/roles/create` | `roles.view` + `roles.create` | |

`permissions_revoked`, the same format as from the role form.

## Error catalog

### HTTP codes

| Code | When |
| ---- | ---- |
| **302 → `/admin/login`** | unauthenticated request; JSON requests get **401** (`apiFetch` then opens the login page) |
| **403** | missing permission (route middleware or FormRequest) or a record above the actor (`UserPolicy`/`RolePolicy`) |
| **404** | model not found, record not in the trash, a backup file that does not exist, single-session sign-out without database sessions |
| **419** | stale CSRF token. Inertia/forms: redirect back with the warning "Страница устарела, повторите действие". `apiFetch`: refreshes the token and retries once |
| **422** | FormRequest validation (including list filters and export formats) or a domain rule (below) |
| **429** | rate limit exceeded |

**Rate limits:**

- `POST /login`: `security.login_throttle` attempts per minute (default 5) for
  the email + IP pair, and four times that per IP across all emails
  (`App\Services\Auth\LoginThrottle::IP_MULTIPLIER`). The client IP is trusted
  only from `TRUSTED_PROXIES`, so a forged `X-Forwarded-For` does not reset the
  limit;
- profile actions that check the current password (`PUT /profile`,
  `PUT /profile/password`, `POST /profile/sessions/logout-others`) share 6
  attempts per minute per user.
