# Documentation

Reference for the template's API surface. This is a server-driven Inertia
application: the "API" is mostly HTTP routes that return Inertia pages or redirects,
plus a handful of JSON endpoints (search, session ping, media). The docs below pin
down contracts that would otherwise have to be inferred from the sources.

## `api/`

| File | What's inside |
|---|---|
| [`api/json-endpoints.md`](api/json-endpoints.md) | The JSON/XHR endpoints and bulk action payloads: request, response shape (snake_case API Resources), authentication (session + CSRF) |
| [`api/permissions-matrix.md`](api/permissions-matrix.md) | Route → permission map (layered model: `permission:` middleware, policies via `can:`, FormRequests, service rules) and error catalog (403/404/422/429 + domain checks) |
| [`api/response-conventions.md`](api/response-conventions.md) | Response types, Inertia shared props, error pages, paginator envelope and list sorting, exports, `/up` health, robots/sitemap, versioning |
| [`api/routes.snapshot.txt`](api/routes.snapshot.txt) | Snapshot of `php artisan route:list` (generated by `composer doc:routes`) |

## Keeping it current

- Route snapshot: `composer doc:routes` after changing `routes/web.php`. It needs
  an application key: without `.env`, set `APP_KEY` in the environment for the
  run. The output width follows the terminal (`COLUMNS=120` matches the
  committed file).
- The other docs are edited by hand — they're small and live next to the code they describe.

> Heavy tooling (Scribe, a generated OpenAPI portal, Postman collections) is
> deliberately **not** wired in: for a template this size, a few JSON endpoints are
> cheaper to describe by hand. If the project grows an external public API, set it
> up under a separate `/api/v1` (see `api/response-conventions.md`) and only then
> bring in a generator.
